## 2026-08-26T13:30:00Z — Stop pytest from polluting the operator's config-integrity seal log (Claude Code)

- **Agent/tool:** Claude Code (remote session)
- **Repos:** dizhaky/hermes-agent
- **Context:** mfc1's Unified Infra Health Check reported `CONFIG INTEGRITY FAIL` repeatedly through 2026-08-25/26, surviving two manual re-seals. Root cause is not config drift: `tests/conftest.py` sandboxes `HERMES_HOME` but not `HERMES_DOTFILES_DIR`, and the config-integrity watchdog resolves `$HERMES_DOTFILES_DIR/hermes/config_integrity.jsonl` at call time. So `save_config` tests writing to a tempdir config still appended seal rows to the operator's real, git-tracked log — **69 of its 149 rows** carried `config_path` under `/private/tmp/pytest-of-danizhaky/…`. Any consumer reading the last row and comparing it to the live config therefore mismatches permanently. The re-seals "worked" only until the next test run.
- **Done:** conftest now sandboxes `HERMES_DOTFILES_DIR` in both places it sandboxes `HERMES_HOME` — at import time (before test modules load) and per-test in `_isolate_env` — and the file's documented hermetic-test invariants gained the matching entry. Mechanism verified against the live watchdog module on mfc1: with the var set, `_log_path()` resolves into the tempdir instead of `~/Dev/dotfiles`.
- **Also (mfc1, operational):** patched `~/.hermes/scripts/unified_infra_health.py` so `latest_seal()` ignores rows whose `config_path` is not the live config — defence in depth for the 69 rows already in the log, which this change cannot retract. With that filter the last genuine seal already matched the live config exactly (`6d58ab36`), no re-seal required, and the whole health check now runs silent.
- **Follow-up:** `unified_infra_health.py` lives only on mfc1 and is untracked — worth adopting into hermes-infrastructure so it is version-controlled and deployable.
