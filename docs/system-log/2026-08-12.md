**The evidence that this was deleted rather than never written:** `config.py`

### What was restored

| function | contract |
|---|---|
| `get_config_lock_path()` | `config.yaml.lock`, beside the config |
| `get_config_seal_path()` | `config.yaml.sha256`, beside the config |
| `config_write_lock()` | exclusive interprocess lock |
| `config_read_lock()` | shared lock; concurrent readers coexist |
| `seal_config()` | record the current hash as the authorized local baseline |
| `verify_config_integrity(locked=False)` | `(ok, current_hash, sealed_hash)` |
| `_reseal_git_backed_integrity_baseline(path)` | refresh the dotfiles JSONL baseline |
| `restore_config(cfg_or_yaml, *, reason="")` | back up, replace, re-seal; returns the backup `Path` |

`save_config()` now calls both sealers after a successful write, which is the
whole point: a write through `save_config` is authorized by definition, so
leaving the baselines stale is what made the watchdog cry tampering at the
model scanner and `/model`.

### Decisions worth stating

**Two "not tampering" cases return OK, deliberately.** A missing config (nothing
to protect yet) and a missing seal sidecar (a config predating sealing) are
both reported ok. Absence of a baseline is not a mismatch, and failing there
would flag every pre-existing install as compromised.

**Sealing can never fail a write.** `seal_config` swallows OSError and the
git-backed reseal catches broadly — it shells into a dotfiles repo outside
Hermes' control, which can be absent, not a git repo, mid-rebase, or read-only.
None of that is a reason to fail a config write that already succeeded.

**The git-backed reseal is a no-op unless the dotfiles directory already
exists.** The watchdog is opt-in, and the skill's `seal()` would otherwise
`mkdir -p` a baseline on machines that never configured one — which the test
`test_save_config_is_a_noop_without_dotfiles_repo` asserts against.

**Locks degrade to no-lock rather than raising.** A platform without a working
primitive, or a home directory that cannot host the lock file, still gets a
readable config; the in-process `_CONFIG_LOCK` continues to order same-process
access. On Windows readers go unlocked, because `msvcrt` has no shared mode and
serialising every read behind an exclusive lock would be worse than the race.

**`restore_config` always writes a pre-restore backup**, even when the live
file is unreadable — a corrupt config is the usual *reason* for a restore, so
that is exactly when the old bytes are worth keeping. The free-text `reason`
is sanitised before it reaches a filename.

**`_expand_value_from_environ` leaves an unset reference verbatim** rather than
blanking it. Substituting "" would turn a typo'd variable into an empty API key
and fail far from the cause; `$NOT_SET` surviving into the config makes the
mistake legible. That single rule also resolves what looked like a
contradiction in its tests — `$TEST_VAR` expands and `literal-$var` does not,
purely because one name is exported and the other is not, with no
case-sensitivity rule needed. It is deliberately **not** wired into config
loading: `_expand_env_vars` walks whole documents and also resolves
`${env:NAME}` SecretRefs with their own warning behaviour, so routing one
through the other would change config semantics rather than restore a helper.

### What was added

**`_mark_exhausted(..., model=...)`** records the bench in
`extra["exhausted_models"][model]` and leaves the credential-wide status alone,
so a 429 on one model does not remove the key from rotation for the others.

*Terminal auth failures are deliberately excluded from the per-model path.* A
revoked or invalid token is dead for every model; recording it per-model would
keep the credential in rotation for the rest and fail instantly on each. The
existing `_is_terminal_auth_failure` classifier makes that call, so the DEAD vs
EXHAUSTED distinction keeps working exactly as before.

**`select(model=...)`** filters entries benched for that model on top of the
existing credential-wide filtering. Keyword-only, so the no-argument callers are
untouched.

**`_prune_expired_model_lockouts()`** drops lapsed records, mirroring what
`_available_entries(clear_expired=True)` already does for the credential-wide
status. It runs *before* filtering, so a lockout that has just expired frees its
credential in the same call rather than one selection later. Without it an
expired record would linger in `extra` forever — harmless to selection, since
the filter checks the deadline, but it would keep appearing in `hermes auth`
and grow without bound across models.

**`reset_statuses()`** now counts a per-model lockout as status. A credential
can be benched for a model while every credential-wide field is clear, and
`reset` has to free that too — otherwise it would report "0 reset" while the
key stayed unusable for that model.

original command still runs; this is display-only. Motivated by the 2026-07-13
incident — a heredoc appending a Slack app-level token to `~/.hermes/.env`,
where the approval prompt reproduced the command in full, so *asking permission
published the credential more widely than running it would have.* The variable
name survives (`SLACK_APP_TOKEN=***`) because the reviewer needs to know which
secret is being written.

`force=True` and `redact_url_credentials=True` are both taken from
`redact_sensitive_text`'s own docstring: `force` is documented for "safety
boundaries that must never return raw secrets regardless of the user's global
logging redaction preference", and someone who disables `security.redact_secrets`
for log verbosity has not asked for their tokens broadcast into Slack. The URL
flag defaults off so actionable OAuth and pre-signed URLs survive ordinary tool
flows — an approval echo is an egress boundary, not a tool flow.

### The fifth test — and two corrections in one finding

`TestSensitiveRedirectPattern::test_redirect_to_sensitive_target` builds
`Path.home() / ".ssh" / "authorized_keys"` and expects it flagged.

**Correction 1.** I first checked `cat key >> /home/alice/.ssh/authorized_keys`,
saw `False`, and called it "a real security gap affecting all users". Wrong:
that path is not the *current* user's home, and the fold is deliberately scoped
to the running user's home. Not folding it is by design.

**Correction 2.** The test failure here really is a root artifact — but it
exposes a genuine narrow gap underneath. `_home_prefix_fold_regex` required
**two components below the root**, which correctly rejects `/` and `/home`
(folding the latter would rewrite every user's path to `~`). `/root` has one
component and is a *legitimate home*, so the count-only rule silently declined
to fold it. The consequence, for any root-run deployment — the shipped Docker
image, CI containers, anything under sudo — is that `~/.ssh/authorized_keys` was
guarded while the identical `/root/.ssh/authorized_keys` was not: the tilde and
absolute spellings of the same file disagreeing.

Replaced the count with the property the guard actually wants: reject a bare
root, and reject a single component only when it *contains* other homes
(`home`, `users`, `var`, `mnt`, …). `/root` folds; `/home` still does not.
Verified both directions — `/root/.ssh/authorized_keys` now flags, `~` still
flags, and `/home/other/.ssh/authorized_keys` is still left unfolded.

### Ninth instalment — CI's own failure list, and the last five

Switched from enumerating failures locally to reading them off CI. That turned
out to matter: the local sandbox reports ~18 failures in `tests/tools/` alone
(missing optional extras, root, no IPv6), while the **whole** CI run for
`9a20a76` failed **2 jobs of 30** — five tests total. CI is the authoritative
list because it is the merge gate; the sandbox list is mostly noise about this
container. Every one of the five turned out to be a real defect, and four of
them are the same shape seen all week: the mechanism survived, its caller did
not.

**1–2. `cron/model_policy.py` had zero callers.** The module is complete and
carefully written — an allowlist of short-retention routes, a denylist for
known prompt-logging ones, a keyword/skill detector that deliberately
over-tags, and `enforce_privileged_model_route()` to raise on a violation. A
repo-wide grep for any of its names found exactly one hit outside the module
itself: the test file. So a legal or finance cron job could be pinned to
`openrouter/owl-alpha` and the guardrail would never run.

Wired it into both write paths. `create_job()` checks the assembled record just
before `save_jobs()`; `update_job()` checks the **merged** record, which is the
part worth stating — the privileged tags come from the stored prompt/skills
(`"HHS settlement monitor"`) while the offending route arrives in `updates`
(`provider="custom:logger"`), so validating either half alone sees nothing
wrong. Both raise before the write, so a rejected job never reaches disk;
`tests/cron/` is 397/397.

**3. The WAL checkpoint had reverted to the strategy that corrupts databases.**
`_try_wal_checkpoint()` carries a sixteen-line docstring explaining that
PASSIVE is required for the periodic path and that the previous TRUNCATE
strategy "caused B-tree corruption on large databases (65K+ pages) due to the
exclusive-lock I/O pressure" — issue #45383. The body executed
`PRAGMA wal_checkpoint(TRUNCATE)`.

Everything around the defect still described the fix: the docstring, the
warning string (`"WAL checkpoint (PASSIVE) failed"`), and the tests. Only the
pragma itself had gone back. This is the most consequential find in the batch —
it is not a dormant code path but the periodic checkpoint on every writer, and
it silently re-opened a corruption bug someone had already diagnosed and
closed. `close()` and the pre-VACUUM path keep TRUNCATE, which is what the
docstring says they should.

Notable: this test passes locally *and* failed in CI for a reason unrelated to
the defect — the runner's SQLite 3.50.4 is on the WAL-reset denylist, so the DB
falls back to `journal_mode=DELETE`. That masked nothing here, but it is the
kind of environment difference that makes "passes locally" worthless as
evidence.

**4. A guard asserting a mechanism nothing uses.**
`test_telegram_slack_matrix_use_bespoke_setup_fn` checked
`gateway._builtin_setup_fn("telegram")`, which now returns `None`: #41112 moved
these three to plugin-registered `setup_fn=interactive_setup`, and the matrix
plugin's version says in its own docstring that it *replaces*
`hermes_cli/setup.py::_setup_matrix`. The invariant the test protects is still
real and still holds — `_configure_platform()` tries the registry entry's
`setup_fn` first, so none of the three reaches `_setup_standard_platform()`,
whose mandatory-first-var behaviour would break Matrix's documented
password-login path. Rewrote the assertion against the dispatch that actually
runs. A guard pinned to a retired lookup is worse than no guard: it fails
loudly for the wrong reason, and would have passed silently had the lookup
merely been renamed.
