### Third instalment — two more production bugs (6 tests)

**`cron/scheduler.py` — a supervisor that could never have started** (5 tests).
`gateway/run.py`'s cron-ticker supervisor does
`from cron.scheduler import get_ticker_heartbeat_age, ticker_heartbeat_is_stale`.
Neither name existed there: `get_ticker_heartbeat_age` lives in `cron/jobs.py`,
and `ticker_heartbeat_is_stale` was defined **nowhere in the repo**. That import
runs inside the supervisor loop, so the watchdog meant to restart a wedged cron
ticker would itself have died on an ImportError the first time it checked.

Added `ticker_heartbeat_is_stale` to `cron/scheduler.py` and re-exported the age
reader beside it, because the supervisor and its tests both treat
`cron.scheduler` as the ticker's public surface (the tests patch
`cron.scheduler.ticker_heartbeat_is_stale`).

The staleness rule is documented rather than invented: `age > interval *
stale_multiplier`, and **an unknown age is not stale**. `get_ticker_heartbeat_age`
returns None for a missing or torn read, and its own docstring says callers must
treat that as "cannot determine", not "dead" — restarting on a torn read would
convert a filesystem hiccup into a restart loop.

**`hermes_cli/providers.py` — provider labels collapsing to their ids** (1 test).
`get_label("xai")` returned `"xai"`, making the xAI API-key entry
indistinguishable from its OAuth sibling in the model picker.

The first fix attempt was wrong and the test said so: I added a fallback at the
end of `get_label`, but that line is unreachable here. For a Hermes-only
provider `get_provider` *does* return a def — one synthesized with
`name=_LABEL_OVERRIDES.get(canonical, canonical)` — so the id was baked in
before any fallback could run. Fixed at that source instead, via a single
`_display_name()` helper used by both call sites: overrides, then the provider
registry in `hermes_cli.models` (which already carries
`ProviderEntry("xai", "xAI", ...)`), then the id.

Deliberately not a new `_LABEL_OVERRIDES` entry: that would be a second copy of
a name the registry already owns, which is the same duplication that produced
the `gateway/status.py` bug above. models.dev is a *remote* catalog, so this
path is also what every provider hits when the catalog is unreachable.

functions of security-adjacent behaviour (sealing, restore, and a config read

`_expand_value_from_environ` is the weakest of the five — nothing in production

That one looks like a test for a feature that was never written.

## 2026-08-12T17:20:00Z — Reconstruct the config-integrity cluster (Claude Code)

Eight functions were missing from `hermes_cli/config.py`, referenced by both
tests and production code. All eight are now restored, and the three test files
that failed at *collection* run green: **36 tests**, 0 failures.

**The evidence that this was deleted rather than never written:** `config.py`
already imports `fcntl as _fcntl` and `msvcrt as _msvcrt` at module scope, in a
try/except pair, and **neither is used anywhere in the file**. Those are the
imports the lock helpers needed. The bridge module
`hermes_cli/config_integrity_cli.py` also still exists, with `_find_core_module`,
`cmd_seal`, `cmd_verify` and `cmd_restore` — the tests import it directly.

### What was restored

| function | contract |
|---|---|
| `get_config_lock_path()` | `config.yaml.lock`, beside the config |
| `get_config_seal_path()` | `config.yaml.sha256`, beside the config |
| `config_write_lock()` | exclusive interprocess lock |
| `config_read_lock()` | shared lock; concurrent readers coexist |
| `seal_config()` | record the current hash as the authorized local baseline |
| `verify_config_integrity(locked=False)` | `(ok, current_hash, sealed_hash)` |
| `_reseal_git_backed_integrity_baseline(path)` | refresh the dotfiles JSONL baseline |
| `restore_config(cfg_or_yaml, *, reason="")` | back up, replace, re-seal; returns the backup `Path` |

`save_config()` now calls both sealers after a successful write, which is the
whole point: a write through `save_config` is authorized by definition, so
leaving the baselines stale is what made the watchdog cry tampering at the
model scanner and `/model`.

### Decisions worth stating

**Two "not tampering" cases return OK, deliberately.** A missing config (nothing
to protect yet) and a missing seal sidecar (a config predating sealing) are
both reported ok. Absence of a baseline is not a mismatch, and failing there
would flag every pre-existing install as compromised.

**Sealing can never fail a write.** `seal_config` swallows OSError and the
git-backed reseal catches broadly — it shells into a dotfiles repo outside
Hermes' control, which can be absent, not a git repo, mid-rebase, or read-only.
None of that is a reason to fail a config write that already succeeded.

**The git-backed reseal is a no-op unless the dotfiles directory already
exists.** The watchdog is opt-in, and the skill's `seal()` would otherwise
`mkdir -p` a baseline on machines that never configured one — which the test
`test_save_config_is_a_noop_without_dotfiles_repo` asserts against.

**Locks degrade to no-lock rather than raising.** A platform without a working
primitive, or a home directory that cannot host the lock file, still gets a
readable config; the in-process `_CONFIG_LOCK` continues to order same-process
access. On Windows readers go unlocked, because `msvcrt` has no shared mode and
serialising every read behind an exclusive lock would be worse than the race.

**`restore_config` always writes a pre-restore backup**, even when the live
file is unreadable — a corrupt config is the usual *reason* for a restore, so
that is exactly when the old bytes are worth keeping. The free-text `reason`
is sanitised before it reaches a filename.

**`_expand_value_from_environ` leaves an unset reference verbatim** rather than
blanking it. Substituting "" would turn a typo'd variable into an empty API key
and fail far from the cause; `$NOT_SET` surviving into the config makes the
mistake legible. That single rule also resolves what looked like a
contradiction in its tests — `$TEST_VAR` expands and `literal-$var` does not,
purely because one name is exported and the other is not, with no
case-sensitivity rule needed. It is deliberately **not** wired into config
loading: `_expand_env_vars` walks whole documents and also resolves
`${env:NAME}` SecretRefs with their own warning behaviour, so routing one
through the other would change config semantics rather than restore a helper.

had the fix.

`uv.lock` exactly.

and three times in `pyproject.toml`). Leaving a version string that disagrees
