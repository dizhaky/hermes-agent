## 2026-08-09T14:05:00Z — Align the Electron version everywhere (Claude Code)

**Repos touched:** `dizhaky/hermes-agent`

### The defect

`apps/desktop/package.json` declared the dependency as `electron: 41.10.3` while
`build.electronVersion` still read `40.10.2`. Those two fields do different jobs:
the dependency (plus the lockfile) decides what `npm ci` installs — what tests run
against and what `electron .` uses in dev — while `build.electronVersion` decides
which Electron dist electron-builder downloads and packages. So the shipped app
was a different Electron from the tested one, and code exercising a 41-only API
would pass CI and fail in the packaged build.

`desktop-electron-pin.test.ts` exists to catch exactly this and was red on `main`.

### A fourth reference, which no test covered

Root `package.json` carries `allowScripts`, keyed by `name@version`, and it still
said `electron@40.10.2`. Electron's postinstall is what fetches the actual binary,
so a stale key means the allowlist silently stops covering it. **Nothing in this
repo reads the field** — no lavamoat dependency, no script, it appears only as data
in the root and `website/` manifests — which is precisely why the drift went
unnoticed. Flagged for a reviewer who knows the external consumer.

### Fix

Aligned **up**, to what is actually installed:

| place | before | after |
| --- | --- | --- |
| `apps/desktop/package.json` dependency | `41.10.3` | unchanged |
| `apps/desktop/package.json` `build.electronVersion` | `40.10.2` | `41.10.3` |
| root `package.json` `allowScripts` | `electron@40.10.2` | `electron@41.10.3` |
| `package-lock.json` resolution | `41.10.3` | unchanged |

Aligning down instead would mean reverting the dependency and regenerating the
lockfile — a larger change, and the resolution could not be verified offline here.
Up is also the safer direction on the merits: ship what you test.

A fourth assertion now pins the `allowScripts` key, so the next bump cannot leave
it behind. It returns early when there is no electron key at all, since not
pinning there is a choice rather than drift.

### Verification

No `node_modules` in this sandbox, and installing the monorepo would drag in the
known `react`/`react-dom` skew, so the test's assertions were executed directly
in Node against the real files — the test reads nothing else. Before: 2 pass, 1
fail (dep vs `build.electronVersion`). After: 4 pass. Positive control:
reverting only the `allowScripts` line fails only the new assertion, and
`node --experimental-strip-types --check` parses the test file.

### Correction to an earlier claim of mine

In PR #156's body and in the 2026-08-08 log I wrote that this mismatch
"arrived in `7e38fa5` (#155, a dependabot bump)". **That was wrong on both
counts.** #155 bumped `dompurify` and `js-yaml` and never touched electron.
`git log` appeared to attribute the lines to it only because this clone is
shallow and `7e38fa5` is the graft boundary, so the whole file reads as added
there. When the drift actually entered is not determinable from this clone, and
I should have checked the diff before naming a culprit.

## 2026-08-09T15:10:00Z — Windows install check, Electron unpacker (Claude Code)

- **Agent/tool:** Claude Code
- **Repos:** hermes-agent
- **Done:**
  - **No Windows host is available in this sandbox, so the install was not
    run.** Everything determining the outcome was checked instead, from the
    lockfile and the published artifact.
  - **The binding ships; the runtime is what is missing.** The
    `@electron-internal/extract-zip@1.0.4` tarball was fetched and its sha512
    matched the lockfile byte-for-byte, so it is exactly what `npm ci`
    installs. It bundles all nine prebuilds — `index.win32-x64-msvc.node`
    included — with no optional platform packages and no postinstall download.
    The first hypothesis, a missing-optional-dependency resolution failure, is
    therefore **wrong**: there is nothing for `npm ci` to fail to resolve.
  - **Root cause, from the PE import table** of the win32-x64 prebuild:
    alongside `KERNEL32`/`ntdll`/`bcryptprimitives` and the
    `api-ms-win-crt-*` Universal CRT (an OS component from Windows 10 on) it
    imports **`VCRUNTIME140.dll`**, which ships with the Visual C++ 2015-2022
    Redistributable and is absent from a clean Windows install. `LoadLibrary`
    then fails, producing exactly the `ERR_DLOPEN_FAILED loading
    index.win32-x64-msvc.node` recorded in the pin test's header. The
    win32-arm64 prebuild imports it too.
  - **Scope:** the package is `"dev": true` in the lockfile — it unpacks
    Electron dists during install and packaging — so this breaks Windows
    *build* machines, not people running a prebuilt installer.
  - **CI cannot catch it.** The only Windows job is `installer-tests.yml`, two
    PowerShell 8.3 short-path tests against `install.ps1`; nothing runs
    `npm ci` or builds the desktop app on Windows. Even if it did, GitHub's
    `windows-latest` carries VS Build Tools, so the redistributable is present
    and the job would pass while a clean developer machine fails.
  - **Documented it** in `apps/desktop/README.md`: the prerequisite beside the
    `npm install` step, plus a troubleshooting entry keyed on the exact error
    string with a `winget` one-liner. Both state that it affects building from
    source, not running an installer.
  - **Added `apps/desktop/scripts/assert-win-vcruntime.mjs`**, wired into
    `prebuilder` so it precedes every `dist:*` and `pack`. It *attempts the
    load* rather than probing System32 for the DLL — testing the real condition
    instead of a proxy, and staying correct wherever the runtime lives.
  - **The guard is a backstop, not the primary fix.** Electron's own postinstall
    unpacks through the same addon, so on an unprepared machine `npm ci` fails
    before any script in this repo runs. The README covers that case; the guard
    covers the electron-builder path (warm npm cache, or a dist download during
    packaging).
  - **Verification:** six tests in `assert-win-vcruntime.test.mjs`, run for real
    rather than re-implemented — vitest is not installed here, so a throwaway
    shim providing `test()` was placed in `node_modules/` for the run and
    removed afterwards. All six pass. Positive controls: neutering the error
    classifier fails 3 of 6; removing the non-Windows early return fails 1 of 6.
    The decision logic takes `platform`, `arch` and an injected `load`, so the
    Windows branch is exercised on Linux.
  - **Not covered by any test:** that a real Windows host without the
    redistributable actually yields `code === "ERR_DLOPEN_FAILED"`. That is
    inferred from the PE import table, not observed.
- **Follow-up:** a `windows-latest` desktop install job would catch resolution
  regressions but not this bug, since the runner has the redistributable;
  reproducing it in CI needs a runner image without it. Not added.
