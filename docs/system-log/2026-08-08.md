- **Done:**
  - **`py/tarslip` — `_install_psutil_android_compat` (`main.py`).**
    `tar.extractall(tmp_path)` with no member validation and no extraction
    filter, on a psutil sdist fetched over the network. The URL is pinned but the
    download's **checksum is never verified**, so a compromised or MITM'd sdist
    could write outside the temp dir via `../` or absolute members. Added the
    same guard `agent/curator_backup.py` already uses — reject traversal members
    up front, then `extractall(..., filter="data")` with a `TypeError` fallback
    for interpreters older than 3.11.4. (The guard was hardened further in the
    second round below — the first version checked names only.)
  - **The sibling copy.** `scripts/install_psutil_android.py:86` had the identical
    unguarded call. Its module docstring says the two copies must be kept in sync
    and removed together, so both are fixed. CodeQL flagged only the `main.py`
    one — its `py/tarslip` query needs a taint path its analysis actually
    traversed, so an equivalent bug in a standalone script went unreported.
  - **`py/incomplete-url-substring-sanitization` — `_infer_stepfun_region`.**
    `if "api.stepfun.com" in normalized` matched by substring, so
    `api.stepfun.com.example.net` inferred `china`. Now parses the host and

- **Third round — merged `origin/main`, and most of this change turned out to be
  superseded.** `main` had refactored the psutil sdist extraction into
  `hermes_cli/psutil_android.prepare_patched_psutil_sdist`, which does not call
  `extractall` at all: it copies file members one at a time with
  `extractfile()` + `copyfileobj()` and refuses every non-file member, so link
  members can't exist in the output. `_install_psutil_android_compat` moved to
  `hermes_cli/update_cmd.py` and calls it; the standalone script imports it too,
  which also retires the duplicated validator. Both psutil-side halves of this
  change are therefore dropped in favour of main's — main's approach is
  structurally better, since it removes the unfiltered fallback rather than
  guarding it. What survives is `assert_safe_tar_members` (still the guard for
  `curator_backup`'s fallback) and the `_infer_stepfun_region` fix.
- **A third real defect, again from Codex review — hardlinks resolve from a
  different base than symlinks.** The guard treated `issym()` and `islnk()`
  identically, resolving both against the link's own directory. That is right
  for a symlink (handed to `os.symlink` verbatim, read by the kernel relative to
  the link) and wrong for a hardlink, which `tarfile` resolves itself against
  the **extraction root** — `TarFile._extract_member` sets
  `tarinfo._link_target = os.path.join(path, tarinfo.linkname)`. So
  `a/b/link -> ../victim` under-resolved to a harmless `a/victim` and passed the
  guard, while `tarfile` linked it to `<root>/../victim`, a file beside the
  destination.
  - **Reproduced end to end before fixing**, not reasoned about: the guard
    accepted the archive, `extractall` produced a link sharing an inode with the
    outside file, and writing through it changed that file's contents. Reachable
    on Python 3.11.0–3.11.3, which is in range for `requires-python = ">=3.11"`.
  - Fixed by picking the base per link type. A test asserts the resulting
    asymmetry directly: the *same* `linkname` is refused as a hardlink and
    allowed as a symlink.

- **Fourth round — Windows path semantics (Codex P2, real).** The guard parsed
  member names with `PurePosixPath`, but `extractall` builds its destination with
  `os.path`, which on Windows also splits on `\` and honours drive letters. A
  member named `..\outside` or `C:\outside` has no `..` part and no leading `/`
  under POSIX parsing and sailed through, while escaping at extraction. Names are
  now rejected if *either* reading says they escape, and link targets resolve with
  `\` treated as a separator. Validation is unconditional rather than
  host-switched: the archive decides whether a name is dangerous, not the machine
  reading it, and a snapshot written on one platform can be restored on another.
  The cost, recorded rather than hidden — a filename that genuinely contains a
  backslash (legal on POSIX) is now refused. 7 cases; positive control fails
  exactly those 7.
- **Disputed and not changed — "symlinked skills can no longer roll back"
  (Codex P2).** The mechanism checks out: `snapshot_skills()` uses
  `tf.add(..., recursive=True)`, which doesn't dereference, so a skill symlinked
  to an absolute path is stored as an absolute-target symlink. But the impact
  claim doesn't: `curator_backup` already extracts with `filter="data"` first, and
  `data` raises `AbsoluteLinkError` (a `TarError`, so the same recovery branch) on
  exactly that member. Verified both side by side. On Python ≥3.11.4 — everything
  CI runs — that rollback was **already failing on `main`**; the guard only makes
  3.11.0–3.11.3 behave the same way. The round-trip gap is a real bug, but it
  belongs on the snapshot side; loosening the guard to admit absolute link targets
  would reopen the escape this change exists to close, for every consumer.
  Recorded as a follow-up.
- **Fifth round — the secret-scan workflow this session added was itself broken,
  in three ways.** It surfaced by failing on this very PR.
  1. **Merging `main` made it re-scan `main`.** A merge commit's diff carries
     everything the merge brought in, so the `BEFORE..AFTER` push range scanned
     60 MB and reported 74 findings, none from the branch. Now excludes commits
     already reachable from the default branch.
  2. **A silently empty scan passed.** The first path-scoped range left a trailing
     space → empty pathspec → git error → gitleaks reported a "partial scan" of
     ~0 bytes and **exited 0**. The check went green having scanned nothing.
     Caught only because the workflow step was extracted from the YAML and run
     verbatim instead of reasoned about. All calls now go through a wrapper that
     treats `failed to scan` / `partial scan` as failure.
  3. **Merge-only content was never scanned at all.** gitleaks walks per-commit
     diffs and never attributes a merge's conflict resolution to anything —
     verified: a key introduced solely in a resolution is invisible even to a
     full-history scan, and shows up only under `--no-git`. A secret committed
     while resolving a conflict passed this check silently. The changed files'
     final content is now scanned as well.
  Also: the content pass initially used the push's before-SHA as its base, which
  on a merge push predates the merge — 7375 files, 126 findings. It measures
  against the default branch now. Verified by running the extracted step for both
  event types (12 commits / 7 files, clean) plus a planted-key control (exit 1).
