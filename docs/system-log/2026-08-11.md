## 2026-08-11T22:20:00Z — Lint the POSIX-path-literal defect instead of hunting it (Claude Code)

**Repos touched:** `dizhaky/hermes-agent`

### Why

The same defect turned up three times in three files across #177 and #180: a
hard-coded absolute POSIX path meeting a path that the code builds with
`path.join`. On Windows `path.join` emits backslashes and `path.resolve`
prepends a drive letter, so the two sides can never be equal — the assertion is
dead on that platform, silently, because the file had only ever run on Linux.

- #177 `update-relaunch.test.ts` — `const ROOT = '/home/u/.hermes/hermes-agent'`
- #177 `windows-hermes-path.test.ts` — `p => p === '/venv/lib/python3.12/site-packages'`
- #180 `ssh-connection.test.ts` — `assert.match(a, /\/[0-9a-f]{16}\.sock$/)`

Two were found by the Windows lane going red, the third by reading the file
before adding it. That is one at a time, after the fact, on a required check.

### What was added

`apps/desktop/eslint-rules/no-posix-path-literals.mjs`, wired into the desktop
ESLint config as `hermes/no-posix-path-literals`.

**It does not ban leading-slash literals.** A blanket ban is unusable: the
seven lane files hold **71** absolute POSIX string literals, and all but the
three above are *inputs* — a fake `execPath`, a ControlPath handed to ssh, a
path the stub filesystem is asked about. Coping with those is the job of the
code under test. The defect is where a literal *meets a computed path*, so the
rule keys on that meeting, in three shapes:

- **joined-root** — `path.join(X, …)` where X is, or is a `const` bound to, an
  absolute POSIX literal. Fix: `path.resolve('/…')`, a no-op on POSIX.
- **comparison** — `x === '/a/b'`, plus the expected slot of an assertion,
  which is the same comparison written through a helper.
- **regex** — a pattern that *opens* with a path separator. "Opens with"
  rather than "contains": `/^#!\/bin\/bash/` is a shebang and
  `/^cd '\/home\/me\/project'…/` is a remote shell command, both legitimately
  POSIX, and both live in lane files today.

Single-segment roots (`'/tmp'`) are ignored, and `path.posix.join` /
`path.win32.join` are exempt because a stated flavour makes the literal
deliberate.

### Scope, and why it is self-maintaining

Applied only to the suites named in `test:desktop:win-install` — and that list
is **parsed from package.json**, not restated in the ESLint config. A second
copy would be one more thing to forget, and the failure mode is silent: a suite
added to the lane but missing from the config gets no cross-platform linting at
exactly the moment it starts needing it. `eslint-rules/windows-lane.mjs` reads
the script and turns each vitest filter into a glob.

Files that only ever run on Linux keep their POSIX literals. This is a
portability rule, not a style rule.

### Verification — observed, not asserted

- **Positive control.** Ran the rule over the pre-fix files (`1770376^`,
  `50e2b2b^`): it reports **exactly** the three known defects (four findings —
  the `ROOT` const is joined twice) and nothing else. Over the current files it
  reports none of them.
- **Self-maintenance, proved rather than claimed.** Dropped a probe test file
  containing a known defect into `electron/`: eslint reported nothing. Added

- **Two false positives, kept and annotated.** `windows-hermes-path.test.ts`
  compares against `/root/venv/Scripts/python.exe` twice. Both are safe: every
  path helper that resolver touches is injected by `makeDeps` and joins with
  `/`, so the value is POSIX on Windows too. They now carry
  `eslint-disable-next-line` with that reason — which is the rule earning its

- **My own tests caught two bugs in the rule** before it ran anywhere.

## 2026-08-11T22:45:00Z — Pin react to one version; the mismatch was breaking CI (Claude Code)

**Repos touched:** `dizhaky/hermes-agent`

### Correction to the entry above

That entry left open "whether CI's js lanes are green only because they resolve
the tree differently." They are not — **CI was failing on this**, and I said
otherwise in passing while triaging #183. I called `get_job_logs` with
`failed_only` at 22:23, saw five Python slices and concluded the JS lane was
clean. The JS jobs had not finished yet; they completed at 22:24–22:25. The
full check-run list for the same run shows:

- `JS & TS checks / web / check` — **failure**, and the log names the cause
  outright: `Incompatible React versions … react: 19.2.8 / react-dom: 19.2.7`,
  4 suites failing at collection.
- `JS & TS checks / apps/desktop / check:test:ui` — **failure**. Same error,
  reproduced locally on a pristine main checkout.
- `All required checks pass` — **failure**, and #183 merged anyway, so that
  aggregator is not gating merges in this repo today.

So the finding was real and understated, not overstated. The lesson is narrow
and repeatable: `failed_only` on a run still in flight reports the failures *so
far*, and reads like a complete answer.

### The fix

Every workspace already declares `react` and `react-dom` at exactly `19.2.7`
(`apps/desktop`, `web`, `apps/bootstrap-installer`; `ui-tui` declares react
only). The stray `19.2.8` came in through transitive **peer** ranges — dozens of
packages ask for `^19` — and npm hoisted that to the root while the four
workspaces kept nested `19.2.7` copies. `react-dom` resolved from the root and
found the root `react`, hence the mismatch.

Added `react` and `react-dom` to the root `overrides`, which is the instrument
this repo already uses for exactly this class of problem (`lodash`, `undici`,
`brace-expansion`). The lockfile result is one react in the tree instead of
five: the four nested `19.2.7` copies collapse and the root drops to `19.2.7`.

- `web check`: 26 files / 165 tests, 0 lint errors.
- `ui-tui check`: 138 files / 1530 tests, 0 lint errors.
- `apps/desktop`: `check:lint` 0 errors, `test:desktop:platforms` 976 passed —
  unchanged, so the override does not disturb the electron side.

## 2026-08-11T23:10:00Z — ink-resize: could not reproduce, made it diagnosable instead (Claude Code)

**Repos touched:** `dizhaky/hermes-agent`

### Correction: it is not a standing red

I described `ui-tui / check` as "still red on CI." That was based on one run.
It **passed on #184's run**, along with every other JS lane and
`All required checks pass`. So the ink-resize failure is **intermittent**, not
persistent, and main is currently green.

### What I could and could not establish

Failed once, on #183's run, in two of the three tests:
`AssertionError: expected 128 to be less than -1` — the erase landed at byte
128 and `hello` was never repainted at all.

Could not reproduce, across a bounded but real attempt:

- 12 isolated runs of `ink-resize.test.ts` — green
- 8 runs under saturating CPU contention (8 spinners on 4 cores) — green
- 3 runs of the whole `hermes-ink` package — green
- the full `ui-tui check` — green

Two mechanisms were probed and **ruled out locally**:

- *"The repaint hadn't flushed when the test asserted."* No: the repaint is
  fully synchronous here. Measured at three stages — after `onRender()`, after
  one microtask, after a 50ms macrotask — `hello` sits at index 39 in all
  three. The `await tick()` is not load-bearing.
- *"Deferred writes from the initial render land after the test clears its
  buffer, shifting the prefix."* This would explain the erase moving from byte
  32 locally to 128 on CI. No: across five runs, zero bytes arrive after the
  clear, at either microtask or macrotask range.

So the mechanism is still unknown. The remaining hypothesis — that the erase
landed in a frame whose repaint went down a diff path with nothing to write —
is exactly the drift bug these tests exist to catch, which means this may be a
real intermittent renderer race rather than a bad test.

### What was changed, and what deliberately was not

**Not changed: the assertion.** Loosening it was the obvious way to make a
flaky test stop flaking, and it is the wrong move here — "erase written,
content never repainted" is the precise failure these tests guard against, so a
weaker check could hide a live bug.

**Changed: the diagnostics.** The three duplicated assertions now go through
`expectErasedThenRepainted(out, text)`, which asserts the same invariant in two
steps — the text was repainted at all, then that it came after the erase — and
carries the frame bytes in the failure message. `expected 128 to be less than
-1` becomes a sentence naming the condition plus the actual bytes written, so
the next occurrence explains itself instead of restarting this investigation.

Verified by negative control: fed the helper the exact CI failure shape and
read the message it produces, rather than assuming it renders.

`ui-tui check`: 138 files / 1530 tests, 0 lint errors.

**Follow-up:** if it recurs, the frame dump should identify the path. Worth
raising the local reproduction attempt to hundreds of runs, or adding a
`--repeat` soak in CI, only if it recurs — it has been seen exactly once.
